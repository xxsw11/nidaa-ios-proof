# PostgreSQL service handoff

This module is the real local PostgreSQL/HTTP implementation; it does not import or execute the in-memory reference model. It reads the existing strict JSON Schema. Notifications use only a database-backed fake adapter, never APNs. Integration execution evidence belongs in the root integration report; Python compilation alone is not integration evidence.

## Runtime and startup contract

- Apply `migrations/001_domain.sql` using the isolated database bootstrap administrator. The schema owner stays the administrator; API role `nidaa_service` has no ownership, superuser, RLS bypass, role creation or DDL privileges. Assign its temporary LOGIN password outside source control.
- Start GoTrue migrations, then apply `002_auth_grants.sql`. API credentials can read `auth.users` and `auth.sessions` for verified identity/revocation checks; cannot mutate Auth tables.
- Apply additive `003_retention_revocation_ledger.sql` before starting this service version. It adds the separately exported withdrawal/block/unblock ledger; the published first migration is unchanged.
- Run `uvicorn Integration.service.main:app --host 0.0.0.0 --port 8000 --no-access-log` inside the private container network. Only the loopback-bound gateway should publish a port.
- API environment: `DATABASE_URL`, `JWT_SECRET`, `AUTH_ISSUER` (fallback `JWT_ISSUER`), `AUTH_URL`, `RECEIPT_KEY`. The latter is an ephemeral Fernet key generated by the harness; it encrypts recoverable invitation tokens in operation receipts. None belongs in the Swift app, repository, logs or artifacts.
- Preserve the private receipt key across stack restarts and any isolated restore that needs still-usable invitation receipt replay. Rotating it without re-encryption makes those receipts unreadable; a database dump must never be treated as a complete key-management backup.
- The privileged maintenance process additionally gets `AUTH_ADMIN_TOKEN` only when executing `cleanup-auth`. The API does not need this administrative credential.
- `GET /health` checks a real database connection without authentication; returns `{"status":"ok","delivery_adapter":"fake"}`.

## HTTP and identity

The `/v1` routes and bodies match `SharedRules/contract.schema.json` and `Docs/IdentitySync/API.md`: commands, operation lookup, account, alert, relationships, sync, current-session logout and revoke-all. Unknown JSON properties fail. Actual received command bodies are limited to 16 KiB, including chunked bodies. The service emits no request bodies/headers or database exception details; infrastructure failure is empty HTTP 503 and therefore an **unknown operation outcome**, not a rejected receipt.

`GET /v1/me` provisions an independent random internal UUID for the verified GoTrue subject. The generic Arabic display label is not identity. A new Auth subject using a formerly deleted email receives no old grants or history. Clients cannot provide actor, bound device, biometric proof or authentication timestamps. Every request validates HS256 signature, issuer, audience, expiry, authenticated role, nonanonymous status, actual confirmed email, actual live provider session, domain account activity and domain session revocation.

Device identity is a separate random UUID bound to each provider session for this trial, not an APNs registration or physical-device attestation. Two B sessions have independent acknowledgement sources and one account-level response. Recent authentication comes exclusively from a signed provider `amr` timestamp for password/OTP/email authentication; `iat`, refresh and recovery do not count. Acceptance, account deletion and revoke-all require evidence at most five minutes old. Refresh alone cannot restore recency.

Logout commits the domain barrier before a best-effort provider logout. Repeated logout is safe. Revoke-all also barriers provider sessions created before the cutoff even if they have never touched the domain API. Provider cleanup failure cannot reactivate a domain session. A same-second login after revoke-all can conservatively be rejected until the next second because provider-session creation is compared at integer-second precision.

## Transaction and table contract

Blocking command/logout work executes in the ASGI thread pool, permitting concurrent HTTP clients to contend through independent PostgreSQL connections. Consent and fake-worker checks also join both live provider users and deny unverified, deleted or currently banned provider accounts; a provider disable does not rely on a later recipient login to suppress queued work.

Each HTTP invocation opens its own psycopg connection. `Domain(conn)` acquires PostgreSQL transaction advisory lock `790182453`, then reads the database clock. The initial isolated trial serializes reads, mutations, expiry, revocation, maintenance and fake worker handoff. This is a deliberate throughput limitation, not a distributed production scalability claim. Transactional savepoints roll back every partially applied domain command on rejection; the outer transaction durably records the rejected receipt and abuse accounting. Receipt, state, outbox and cursor updates commit together.

Schema `nidaa` contains normalized `accounts`, `sessions`, `invitations`, `grants`, `blocks`, `alerts`, `recipients`, `acknowledgements`, `operations`, `outbox`, `fake_handoffs`, `history_hides`, `removals`, `rate_events`, and `deletion_ledger`. Columns and constraints are authoritative in `001_domain.sql`. All domain timestamps are integer UTC seconds; provider timestamps retain provider types. All tables force RLS. `authenticated` can SELECT but has no matching policy, so obtains zero rows; neither `anon` nor `authenticated` can write. Service-specific policies enable the trusted command service. No SQL RPC or security-definer bypass is exposed.

Important fixture columns:

| Table | Fields |
|---|---|
| accounts | user_id, subject, active, email, display_name, cursor, revoked_before |
| sessions | session_id (provider), user_id, device_id, auth_at, revoked |
| invitations | invitation_id, sender_id, intended_email, token_digest, state, expires_at, created_at, accepted_by |
| alerts | alert_id, sender_id, state, version, created_at, expires_at, closed_at |
| recipients | alert_id, user_id, response, response_version, access, attempts, provider_accepted |
| outbox | job_id, alert_id, recipient_id, ordinal, state, created_at, deadline |

| deletion_ledger | ledger_id, user_id, subject, requested_at, provider_completed |

Invitations permit ten issuances per sender/day, three pending invitations per sender/target, a 60-second target cooldown, five acceptance attempts/account/minute; creates permit five/account/minute. Failed attempts consume relevant rate accounting. Production ingress/IP protections and protection against mass account creation remain outside this isolated trial.

## Internal worker and maintenance

```text
python -m Integration.service.worker dispatch
python -m Integration.service.worker dispatch --job <job UUID>
python -m Integration.service.worker dispatch --job <job UUID> --crash-before-commit
python -m Integration.service.worker dispatch --job <job UUID> --crash-after-commit
python -m Integration.service.worker purge
python -m Integration.service.worker export-ledger --file <private ledger file>
python -m Integration.service.worker replay-ledger --file <private ledger file>
python -m Integration.service.worker cleanup-auth
```

Before-commit injection exits 71 after rollback; after-commit injection exits 72 after the transaction commits. These are private CLI flags, never HTTP features. The fake handoff ledger and outbox state share a transaction and unique job key, so a restart cannot duplicate a committed fake handoff. This **does not prove exactly-once external notification delivery**: no external notification call exists. Worker execution independently rechecks consent, blocks, account deletion, expiry, recipient access and response.

Purge removes alert details 30 days after closure and operation receipts/removal markers after 90 days. Invitation secrets disappear on use/cancel/expiry/deletion; old invite records are purged 30 days after their expiry. These are provisional project choices, not legal requirements. Full snapshots are account-scoped and replace local replicas, so absent records cannot survive a legitimate newer full synchronization. No partial pages masquerade as full snapshots. This trial has no delta feed or pagination and is intended only for its bounded fictional test accounts.

Delete-account commits immediate inactivity, revokes domain sessions, removes profile/contact data, suppresses pending work, cancels own active alerts, invalidates consents/invitations and writes the deletion ledger. The separate privileged worker deletes the actual provider user through GoTrue's Admin API. It is retryable; deletion remains effective while cleanup is delayed.

For an isolated backup drill: export the current deletion ledger separately; restore the pre-deletion database into an inaccessible dedicated database; replay the ledger **before opening any service connection to clients**; run provider cleanup against the correspondingly restored isolated Auth instance if needed; then verify deletion barriers and purges. The ledger contains pseudonymous identifiers and is private maintenance material, never a test artifact. Ledger replay is idempotent and reinstates the barrier even when the account is absent from that backup. Automatic ledger expiry is deliberately disabled until backup inventory/restore verification can prove expiry safe; production backup retention and offsite ledger integrity remain unproven.

No public backend, external email, APNs, production authentication hardening, encrypted database disks or physical-device notification behavior is claimed by this module.

## Retention and revocation restore amendment

Email-address changes are deferred in this trial; the loopback gateway rejects user updates containing an email change while retaining the password-recovery flow. Independently, consent and worker processing compare both providers' current canonical emails against the stored account contact attributes and fail closed on a mismatch. A privileged test change cannot authorize a queued handoff under an old address before the next login observes it. A complete production email-change/reverification/session-revocation journey is not claimed.

Read-time retention now inserts a unique `(account, alert)` removal marker and advances each affected account's cursor when its 30-day history expires, even before a sweeper physically deletes it. Repeated reads do not advance that cursor again for the same retention removal. A client that applies only strictly newer full snapshots can therefore remove expired cached details promptly after reconnecting.

The independent ledger export now includes `revocations` as well as `deletions` in format 1. Revocation entries contain opaque UUIDs, a transaction-serialized ordinal, action (`withdraw`, `block`, `unblock`) and server time. They contain no profile or invitation secret. Withdrawal and blocking record the barrier in the same transaction as grant/access/outbox changes. Unblocking is also recorded so a restore replays the final block order; it never restores a sending grant.

Restore accepts legacy deletion-only exports for compatibility, but those **cannot establish withdrawal/block safety**. The current complete export must be retained independently of the backup and replayed, ordered by ordinal, before reopening the restored service. Revocations apply before account deletions, so deletion remains final. The CLI reports deletion and revocation replay counts separately. No ledger event is automatically expired while backup inventory remains unspecified.

Conservative restore policy: a pair with any historical withdrawal/block requires new explicit consent after restoration, even if a later acceptance was present in the backup. Replay does not synthesize affirmative consent. This may temporarily revoke a legitimately reaccepted pair, but prevents an old backup from silently restoring permission. A fresh invitation/acceptance can establish a new grant after the isolated recovery gate. Withdrawal/block also keeps historical alert access unavailable; later consent never restores those old alerts.
